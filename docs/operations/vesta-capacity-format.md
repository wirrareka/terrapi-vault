# Typed receipt capacity format 2

Format 2 raises the typed lifetime receipt-count ceiling from 100,000 to 1,000,000 while retaining the independent 256 MiB encoded-receipt ceiling. It never expires, deletes, or reinterprets an operation ID. Application rows remain governed by the unchanged SQL snapshot limits.

Upgrade a stopped, healthy pair only after a verified backup. Open both members with the current binary, confirm equal committed checkpoints, run `upgrade_receipt_capacity` on each member, run `audit_snapshot_capacity` on each, and require equal results before admitting writes. The migration validates the complete receipt prefix, creates the accounting row and triggers, then flips `receipt_format` to 2 last in the same SQLite transaction. A legacy binary expects receipt format 1 and therefore rejects the upgraded file.

The ledger is admission accounting, not idempotency authority. `operation_receipts` and the checkpoint receipt digest remain authoritative, and normal checkpoint/admission validation continues parsing receipt content. The migration performs that authoritative checkpoint/prefix validation inside the same transaction before creating the ledger and flipping the marker. Format 2 makes receipt rows immutable with authenticated trigger definitions; inserts update exactly one bounded ledger row or abort. Reopen and restricted-maintenance admission validate the exact normalized table/trigger type, binding, and SQL plus the counters. Format 1 rejects orphan format-2 objects. Exact old retries and conflicting reuse retain their existing behavior. Snapshot format 2 carries the expanded count contract; restore recomputes accounting from validated pages rather than trusting caller-provided counters.

Capacity-format 2 does not make all writes O(1): application snapshot measurement and checkpoint receipt validation remain linear, while publication, audit, restore, and upgrade stream the complete history. The one-million ceiling is therefore a format bound, not a throughput promise. Production qualification must record representative p50/p95 write, checkpoint, publication, and restore latency plus database/WAL/staging size and peak memory on every supported native platform.

Downgrade and mixed-binary operation are unsupported. Keep the old binary only for pre-upgrade backups. A ledger mismatch, incomplete trigger/table set, receipt corruption, sequence gap, unsupported marker, or over-limit snapshot must fail closed; operators must restore a verified generation rather than editing accounting metadata.
